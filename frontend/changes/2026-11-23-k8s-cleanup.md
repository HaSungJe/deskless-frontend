# 프론트 요청 — Docker 실행 구성 정리 · 백엔드 모니터링 결합 끊기 · 헬스 체크

- 보낸 곳: deskless (2026-11-23)
- 받는 곳: [deskless-frontend](https://github.com/HaSungJe/deskless-frontend)
- 기준 커밋: `531dee3`
- 화면 · API 변화: 없음

## 왜

deskless 저장소가 백엔드 · 프론트를 쿠버네티스(k3s · Helm)로 엮는다. **"어떻게 띄우는가"**(인스턴스 수 · 포트 노출 · 네트워크 · 지표 수집)는 deskless 가 맡고, 프론트는 **"무엇을 띄우는가"**(앱 코드 + `Dockerfile`)만 갖는다.

지금 프론트 `docker-compose.yml` 은 백엔드가 만드는 모니터링 망(`deskless-monitoring`, external)에 붙어야 떠서, 백엔드 Docker 묶음을 먼저 띄운 서버에서만 실행된다. 백엔드도 같은 정리를 하며(`requests/backend/2026-11-23-k8s-cleanup.md`) Prometheus · Grafana 는 deskless 로 옮긴다 — 그래서 이 결합이 없어진다.

### 정해진 것 (사용자 결정 2026-11-23)

- **compose 는 지운다** — 개발은 `npm run dev`, 배포는 deskless 차트. 프론트에는 `Dockerfile` · `.dockerignore` 만 남긴다.
- **지표 서버(`src/metrics-server.ts`)는 남는다** — `/metrics` 를 내는 쪽은 앱이다. 모으는 쪽(Prometheus 수집 대상 `web`)이 deskless 로 간다.
- **헬스 체크는 백엔드와 같은 계약** — 지표 전용 포트에 `/health/live` · `/health/ready`(아래 2절).

## 2. 더하는 것 — 헬스 체크 (쿠버네티스 프로브)

### 계약 (백엔드 앱 4개와 같다)

| 경로 (지표 전용 포트 — Docker · 쿠버네티스 9464, 로컬 9468) | 200 | 503 |
|---|---|---|
| `GET /health/live` | 프로세스가 응답하면 항상 | — |
| `GET /health/ready` | 서버가 요청을 받을 준비가 됨 | 준비 전 · 종료 중 |

- 상태 코드가 계약이다 — 본문은 프로브가 보지 않는다(짧게 `{"status":"ok"}` · `{"status":"not_ready"}`).
- 백엔드 API 가 응답하는지는 보지 않는다 — 백엔드가 잠깐 끊길 때 프론트 파드까지 모두 준비 안 됨이 되는 것을 피한다.
- Next.js 라우트로 열지 않는다 — 지금 지표처럼 전용 포트로만(공개 주소에 노출하지 않는다).

### 구현 메모

- 지표 서버의 라우팅(`src/metrics-server.ts:51` — 지금은 `/metrics` 외 404)에 두 경로를 더한다.
- 준비 시점: `instrumentation.ts` 의 `register()` 는 요청을 받기 전에 끝난다(`src/instrumentation.ts:2`). 본 포트가 열리는 정확한 시점을 알 수 없으면 `register()` 완료를 준비됨으로 봐도 된다 — 짧은 틈은 deskless 프로브의 첫 확인 지연으로 흡수한다.
- 종료 처리 주의: `process.on('SIGTERM')` 리스너를 더하면 Node 의 기본 종료 동작이 사라진다. Next 서버가 스스로 종료를 처리하는지 확인한 뒤에만 더하고, 확실하지 않으면 종료 때 503 전환은 빼도 된다 — 종료 전 대기(preStop)는 deskless 차트가 맡는다.
- 테스트는 이 저장소 규칙대로(`src/test/metrics-server.test.ts` 가 이미 있다).
