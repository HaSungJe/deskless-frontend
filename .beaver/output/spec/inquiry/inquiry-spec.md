# 문의 — 이용자 문의와 업체 · 관리자 답변

## 한눈에

- **무엇을** 이용자가 업체나 바로방에 카테고리를 골라 문의하고 답변을 보며, 업체 관리자는 자기 업체 문의에, 관리자는 바로방 문의에 답변하고 스팸 · 도배 문의를 한 건씩 블라인드한다.
- **왜** 이용자가 업체나 운영에 물어볼 통로가 없다(백엔드 수정 요청 `frontend/changes/2026-11-24-inquiry.md` — 새 API 10개).
- **범위 밖** 여러 문의를 골라 한꺼번에 처리하기(API 없음), 문의 고치기 · 지우기(이용자 — API 없음), 답변 알림(문자 · 푸시).

| 진입점 | 한 줄 요약 | 테스트 |
|---|---|---|
| 1. 내 문의 목록 | 내 정보 → 문의 · 카테고리 · 상태 칩 · 카드 · 문의 대상 이름 | 3건 |
| 2. 문의하기 | 대상(바로방 · 업체 검색 + 지도) · 카테고리 · 제목 · 내용 · 동의 → 등록 | 5건 |
| 3. 내 문의 상세 | 내용 · 답변 · 블라인드 안내 | 2건 |
| 4. 문의 관리 목록 | 업체 관리자(내 업체) · 관리자(바로방) — 카테고리 · 상태 · 검색 · 표 | 2건 |
| 5. 문의 관리 상세 | 답변 등록 · 수정 · 블라인드 · 해제 · 할 수 있는 일 | 7건 |

## 1. 내 문의 목록 — `PAGE /inquiries`

**동작 흐름**

1. **들어오기** — 내 정보의 "문의" 줄을 누르면 문의 목록으로 온다(로그인한 이용자만 — 아니면 로그인 화면을 거쳐 돌아온다).
2. **목록 읽기** — 카테고리 목록과 내 문의 1쪽(전체 · 최신순)을 읽는다.
3. **거르기** — 카테고리 칩(전체 + 받은 카테고리) · 상태 칩(전체 · 접수 · 답변완료 · 블라인드)을 누르면 1쪽부터 다시 읽는다.
   - "전체"면 → 그 값을 빼고 부른다
4. **쪽 넘기기** — 아래 페이지 번호로 다른 쪽을 읽는다.
5. **이동** — 카드를 누르면 내 문의 상세로, 위의 "문의하기"를 누르면 문의하기로 간다.

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `inquiry_category_id` | | 카테고리 칩 — 받은 카테고리 ID, 전체면 보내지 않는다 |
| `inquiry_state_id` | | 상태 칩 — 접수 `RECEIVED` · 답변완료 `ANSWERED` · 블라인드 `BLIND`, 전체면 보내지 않는다 |
| `page` | ✓ | 보는 쪽(처음 1) |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 들어온 뒤 "결제/환불" · "답변완료" 칩을 누른다 | 카테고리 목록 1번 · 처음 목록 1번(값 없이 · 1쪽) → 목록 다시(`PAYMENT` · `ANSWERED` · 1쪽). 카드: 상태 배지 · 카테고리 · 제목 · 대상(아래 계산 규칙) · 문의일, 답변이 있으면 답변일 | ✓ 정상 |
| 바로방에 한 문의 | 대상이 "바로방" | — (계산 규칙) |
| 문의가 없다(처음 · 거른 뒤) | "아직 문의가 없어요" · 거른 뒤면 "다른 조건을 골라 보세요" 안내 | — (공통 빈 안내) |
| 목록을 못 읽었다 | 받은 문구 | — (공통 실패 처리) |

**계산 규칙 — 문의 대상 이름**

검증: 업체에 한 문의는 상호명, 업체가 없는 문의는 서비스 이름으로 보인다.

| 확인하는 것 | 입력 | 기대 결과 |
|---|---|---|
| 업체에 한 문의는 상호명이 보인다 | 상호명 "바로방 강남역점" | `바로방 강남역점` |
| 업체가 없는 문의는 서비스 이름이 보인다 | 상호명 없음 | `바로방`(사이트 이름) |

## 2. 문의하기 — `PAGE /inquiries/new`

**동작 흐름**

1. **들어오기** — 문의 목록의 "문의하기", 또는 업체 상세의 "이 업체에 문의"로 온다(로그인한 이용자만).
   - 업체 상세에서 왔으면(`?store_id=`) → 그 업체를 읽어 대상에 골라 둔다
2. **대상 고르기** — "바로방에 문의" · "업체에 문의" 중 고른다. 업체면 이름을 검색해(검색 버튼 · Enter) 결과(사진 · 상호명 · 주소 · 지도)에서 하나를 고른다.
   - 검색어가 비었으면 → "검색어를 입력해주세요." 검색 칸 옆, 검색하지 않는다
   - "지도"를 누르면 → 팝업에 그 업체 핀 하나짜리 지도
3. **내용 쓰기** — 카테고리(받은 목록 칩) · 제목(100자) · 내용(2000자)을 넣고 개인정보 수집 · 이용 동의에 체크한다.
4. **검사** — "문의 등록"을 누르면 동의 체크와 입력(DTO)을 검사한다.
   - 동의하지 않았으면 → 동의 칸 옆에 문구, 등록하지 않는다
   - 입력이 틀리면 → 칸 옆에 문구, 등록하지 않는다
5. **등록** — 문의 등록(큐)을 부른다. 업체를 골랐으면 `store_id` 를 넣고, 동의 값은 보내지 않는다.
   - 등록되면 → 그 문의 상세로
   - 결과 없이 끝나면 → 문의 목록으로
   - 서버가 거절하면 → 받은 문구(칸 오류는 칸 옆)

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `keyword` | 업체 검색 때 ✓ | 업체 이름 검색어(50자까지) — 등록에는 보내지 않는다 |
| `store_id` | | 고른 업체 — "바로방에 문의"면 보내지 않는다 |
| `inquiry_category_id` | ✓ | 카테고리 — 받은 목록에서 하나 |
| `title` | ✓ | 제목(100자까지) |
| `content` | ✓ | 내용(2000자까지) |
| 동의 체크 | ✓ | 화면에서만 확인 — 서버로 보내지 않는다 |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| "업체에 문의" → "강남"으로 검색해 결과 하나를 고르고, 카테고리 · 제목 · 내용 · 동의를 채워 등록한다 | 업체 검색 1번(`강남`) → 등록(큐) 1번(`{store_id, inquiry_category_id, title, content}` — 동의 값 없음) → 그 문의 상세(`/inquiries/<문의>/`)로 | ✓ 정상 |
| "바로방에 문의"로 등록한다 | 등록(큐) 1번 — `store_id` 없이 | ✓ 정상 |
| 업체 상세의 "이 업체에 문의"로 들어온다 | 업체 상세 1번(그 업체) → 대상 "업체에 문의" · 그 업체(사진 · 상호명 · 주소)가 골라져 있다 | ✓ 정상 |
| 동의에 체크하지 않고 등록한다 | "개인정보 수집 · 이용에 동의해주세요." 동의 칸 옆 · 등록 0번 | ✓ 검증 실패 |
| 카테고리를 고르지 않고 등록한다 | "카테고리를 선택해주세요." 카테고리 칸 옆 · 등록 0번 | ✓ 검증 실패 |
| 검색 결과가 없다 | "검색 결과가 없어요" | — (보여 주기만) |
| "지도"를 누른다 | 팝업 지도에 그 업체 핀 하나(끌기 · 확대 끔) | — (보여 주기만 — 공통 지도 부품) |
| "업체에 문의"인데 업체를 고르지 않았다 | 등록 버튼이 꺼져 있다 | — (보여 주기만) |
| 등록이 결과 없이 끝난다(큐 pending) | 문의 목록으로 | — (입점 신청과 같은 흐름) |
| 서버가 거절한다(업체를 찾을 수 없음 등) | 받은 문구 | — (공통 실패 처리) |
| `?store_id=` 의 업체를 못 읽었다 | 받은 문구 · 대상은 고르기 전 상태 | — (공통 실패 처리) |

## 3. 내 문의 상세 — `PAGE /inquiries/[inquiry_id]`

**동작 흐름**

1. **상세 읽기** — 들어오면 내 문의 하나를 읽는다(로그인한 이용자만).
   - 남의 문의 · 없는 문의면 → 받은 문구와 목록으로 가는 링크만
2. **블라인드 안내** — 상태가 블라인드면 위에 "스팸/반복성 문의로 블라인드 된 문의입니다." 띠를 보인다(내용은 그대로).
3. **보이기** — 상태 배지 · 카테고리 · 대상 · 제목 · 문의일 · 내용, 답변이 있으면 답변 내용 · 답변일, 없으면 "아직 답변이 없어요".

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `inquiry_id` | ✓ | 주소의 문의 ID |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 답변이 달린 업체 문의를 연다 | 상세 1번 — 답변완료 배지 · 카테고리 · 상호명 · 제목 · 내용 · 답변 내용 · 답변일 | ✓ 정상 |
| 블라인드된 문의를 연다 | "스팸/반복성 문의로 블라인드 된 문의입니다." 띠 · 내용은 그대로 | ✓ 정상 |
| 답변 전 문의 | 답변 자리에 "아직 답변이 없어요" | — (보여 주기만) |
| 남의 문의 · 없는 문의 | 받은 문구 · 목록 링크 | — (공통 실패 처리) |

## 4. 문의 관리 목록 — `PAGE /manager/inquiries` · `/admin/inquiries`

**동작 흐름**

1. **들어오기** — 콘솔 왼쪽 메뉴 "문의"로 온다. 업체 관리자는 내 업체 문의(모든 업체 관리자), 관리자는 업체가 아닌 바로방 문의만 본다.
2. **목록 읽기** — 카테고리 목록과 문의 1쪽(전체 · 최신순)을 읽는다 — 업체 관리자는 `/mine` 경로, 관리자는 `/mine` 없는 경로.
3. **거르기** — 카테고리 고르기 · 상태 칩(전체 · 접수 · 답변완료 · 블라인드) · 검색어(제목 · 내용) 조회로 1쪽부터 다시 읽는다.
4. **쪽 넘기기** — 아래 페이지 번호로 다른 쪽을 읽는다.
5. **상세로 이동** — 제목을 누르면 그 영역의 문의 관리 상세로 간다.

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `inquiry_category_id` | | 카테고리 — 전체면 보내지 않는다 |
| `inquiry_state_id` | | 상태 칩 — `RECEIVED` · `ANSWERED` · `BLIND`, 전체면 보내지 않는다 |
| `keyword` | | 검색어(100자까지) — 비면 보내지 않는다 |
| `page` | ✓ | 보는 쪽(처음 1) |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 업체 관리자가 카테고리 · 접수 · 검색어로 조회한다 | 카테고리 목록 1번 · 처음 목록 1번(`/mine`, 값 없이 · 1쪽) → 목록 다시(`/mine`, 그 카테고리 · `RECEIVED` · 검색어 · 1쪽). 표: 번호 · 카테고리 · 제목(상세 링크 `/manager/inquiries/<문의>/`) · 작성자 닉네임 · 상태 · 답변일시 · 문의일시 | ✓ 정상 |
| 관리자가 들어온다 | 같은 화면이 관리자 경로(`/mine` 없음)로 읽고, 제목 링크가 `/admin/inquiries/<문의>/` | ✓ 정상 |
| 조건에 맞는 문의가 없다 | "조건에 맞는 문의가 없습니다." · 거르기를 풀거나 검색어를 지워 보라는 안내 | — (공통 빈 안내) |
| 업체 관리자의 업체가 탈퇴 · 삭제됐다(404) | 받은 문구 | — (공통 실패 처리) |
| 목록을 못 읽었다 | 받은 문구 | — (공통 실패 처리) |

## 5. 문의 관리 상세 — `PAGE /manager/inquiries/[inquiry_id]` · `/admin/inquiries/[inquiry_id]`

**동작 흐름**

1. **상세 읽기** — 들어오면 문의 하나를 그 영역 경로로 읽는다.
   - 범위 밖 · 없는 문의면 → 받은 문구와 목록으로 가는 링크만
2. **할 수 있는 일** — 상태 · 답변 유무로 답변 버튼 글자 · 답변 칸 막힘 · 블라인드 버튼 글자를 정한다(아래 계산 규칙).
3. **답변** — 답변 칸(2000자, 지금 답변이 채워져 있음)에 쓰고 "답변 등록" · "답변 수정"을 누르면 검사 뒤 답변(큐)을 부르고, 띠를 보인 뒤 상세를 다시 읽는다.
   - 비었으면 → "답변을 입력해주세요." 칸 옆, 부르지 않는다
4. **블라인드 · 해제** — 버튼을 누르면 확인 창 뒤에 블라인드 · 해제(큐)를 부르고 상세를 다시 읽는다.
   - 취소하면 → 부르지 않는다
   - 서버가 거절하면 → 받은 문구(이미 블라인드 · 블라인드가 아님 · 블라인드된 문의에 답변)

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `inquiry_id` | ✓ | 주소의 문의 ID |
| `answer_content` | 답변 때 ✓ | 답변(2000자까지) — 다시 보내면 통째로 바뀐다 |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 업체 관리자가 답변 없는 문의에 답변을 쓰고 "답변 등록"을 누른다 | 답변(큐) 1번(`/mine/<문의>/answer`, `{answer_content}`) → "답변을 등록했어요." 띠 → 상세 다시(상세 2번) | ✓ 정상 |
| 답변을 비우고 누른다 | "답변을 입력해주세요." 칸 옆 · 답변 0번 | ✓ 검증 실패 |
| 관리자가 "블라인드"를 누르고 확인한다 | 확인 창 → 블라인드(큐) 1번(`/<문의>/blind`) → 상세 다시(상세 2번) | ✓ 정상 |
| 블라인드된 문의에서 "블라인드 해제"를 누르고 확인한다 | 확인 창 → 해제(큐) 1번(`/unblind`) → 상세 다시(상세 2번) | ✓ 정상 |
| 확인 창에서 취소한다 | 창 닫힘 · 블라인드 · 해제 0번 | — (공통 확인 창) |
| 답변이 있다 | 답변 칸 아래 "마지막 답변 <계정 이름> · <답변일시>" | — (보여 주기만) |
| 서버가 거절한다 | 받은 문구 | — (공통 실패 처리) |
| 범위 밖 · 없는 문의 | 받은 문구 · 목록 링크 | — (공통 실패 처리) |

**계산 규칙 — 관리 상세에서 할 수 있는 일**

## 데이터 변화

- 문의하기(2)는 문의 하나를 만든다(백엔드 큐 — 접수 상태). 동의 값은 어디에도 저장하지 않는다.
- 답변(5)은 문의의 답변을 쓰거나 통째로 바꾸고 답변완료로 둔다. 답변한 계정 · 시각이 남는다.
- 블라인드(5)는 문의를 블라인드로 두고(답변은 그대로), 해제하면 답변이 있던 문의는 답변완료 · 없던 문의는 접수로 돌아간다.
- 목록 · 상세는 읽기만 한다. 화면이 따로 저장하는 값은 없다.
