# 관리자 콘솔 — 콘솔 틀 · 관리자 로그인 · 비밀번호 변경

## 한눈에

- **무엇을** 총괄관리자 · 관리자가 `/admin/login` 에서 아이디 · 비밀번호로 로그인하고, 왼쪽 메뉴 · 상단 바가 있는 관리자 콘솔에 들어와 비밀번호를 바꾸거나 로그아웃한다. 처음 로그인한 계정은 바로 비밀번호 변경으로 간다.
- **왜** 관리자 영역(`/admin`)에 들어갈 길이 없고, 앞으로 만들 관리자 화면(대시보드 · 입점 신청 · 업체 · 업체 관리자 · 이용자)이 들어갈 틀이 없다.
- **범위 밖** 대시보드(Phase 17 — 그 전까지 첫 화면은 "준비 중" 안내), 입점 신청 · 업체(Phase 16), 업체 관리자 · 이용자(Phase 17) — 그 전에는 메뉴를 눌러도 없는 화면. 아이디 찾기 · 비밀번호 초기화(관리자에게는 없다), 기기 알림 토큰(`device_os` · `device_token` — 웹은 보내지 않는다).

| 진입점 | 한 줄 요약 | 테스트 |
|---|---|---|
| 1. 콘솔 틀 | 왼쪽 메뉴 5개 · 상단 바(계정 · 비밀번호 변경 · 로그아웃) · 첫 화면 준비 중 안내 | 1건 |
| 2. 관리자 로그인 | 아이디 · 비밀번호로 로그인, 처음이면 비밀번호 변경으로 | 4건 |
| 3. 로그인 처리 | Next 서버가 백엔드 로그인 → 토큰 · 계정 쿠키 | 2건 |
| 4. 비밀번호 변경 | 콘솔 안에서 현재 · 새 비밀번호 | 2건 |

---

## 1. 콘솔 틀 — `PAGE /admin/…`

**동작 흐름**

1. 로그인 뒤 관리자 화면(`/admin/…`)은 모두 이 틀 안에 그린다. 로그인하지 않았으면 관리자 로그인(2)으로 보낸다 — 돌아올 주소를 들고.
2. 들어오면 로그인 때 기억한 계정(아이디 · 권한)을 읽어 상단 바에 아이디 · 권한 배지(총괄관리자 / 관리자) · "비밀번호 변경" · "로그아웃"을 보여 준다.
3. 왼쪽 메뉴는 대시보드 · 입점 신청 · 업체 · 업체 관리자 · 이용자 — 총괄관리자 · 관리자 모두 같다. 지금 화면의 메뉴를 강조하고, 화면이 좁으면 메뉴가 본문 위로 쌓인다.
4. 첫 화면(`/admin`)은 대시보드가 생길 때까지 "대시보드는 준비 중이에요" 안내만 보여 준다.
5. 로그아웃하면 관리자 토큰 · 계정 쿠키를 지우고 관리자 로그인 화면을 새로 연다.

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| (없음) | | 계정은 토큰과 로그인 때 기억한 쿠키로 안다 |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 총괄관리자가 들어와 로그아웃한다 | 상단 바(아이디 · "총괄관리자" 배지) · 메뉴 5개 → 쿠키 삭제 1번 → 관리자 로그인 화면을 새로 연다 | ✓ 정상 |
| 로그인하지 않았다 | 관리자 로그인(돌아올 주소) | — (공통 로그인 가드) |
| 계정 쿠키가 없다(쿠키를 지웠다) | 아이디 · 배지 없이 — 다시 로그인하면 돌아온다 | — (업체 콘솔 틀과 같은 처리) |
| 첫 화면에 들어온다 | "대시보드는 준비 중이에요" 안내 | — (보여 주기만 — Phase 17 에서 대시보드로 바뀐다) |
| 아직 없는 화면 메뉴를 누른다 | 없는 화면(Phase 16 · 17 에서 생긴다) | — (범위 밖) |

## 2. 관리자 로그인 — `PAGE /admin/login`

**동작 흐름**

1. 메뉴 없이 바탕 가운데 카드 — "관리자 로그인" 제목, "총괄관리자 · 관리자 계정으로 로그인합니다.", 아이디 · 비밀번호, "로그인", 카드 아래 "관리자 계정은 아이디 찾기 · 비밀번호 초기화를 제공하지 않습니다."
2. 이미 관리자로 로그인했으면 돌아갈 주소로 보낸다.
3. "로그인"을 누르면 아이디 · 비밀번호를 검사해 틀린 칸 옆에 오류를 보이고, 맞으면 로그인 처리(3)를 부른다.
4. 되면 처음 로그인한 계정(비밀번호 변경 필요)은 비밀번호 변경(4)으로, 아니면 돌아갈 주소(없으면 첫 화면)로 간다.
5. 안 되면 아이디 칸 위에 위험 띠 — 틀린 정보는 "잘못된 로그인 정보입니다."(아이디 · 비밀번호 중 무엇이 틀렸는지 가르지 않는다), 정지 계정은 받은 문구와 "사유: …". 비밀번호 칸만 비운다.

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `login_id` | ✓ | 아이디(30자까지) |
| `login_pw` | ✓ | 비밀번호(20자까지) |
| `return_url` | | 로그인 뒤 돌아갈 주소(같은 사이트만) |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 맞는 아이디 · 비밀번호로 로그인한다 | 로그인 처리 1번(앞뒤 빈칸을 뗀 아이디) → 돌아갈 주소 | ✓ 정상 |
| 처음 로그인한 계정으로 로그인한다 | 비밀번호 변경 화면(처음 로그인 안내 띠) | ✓ 정상 |
| 정지 계정으로 로그인한다 | 위험 띠 — 받은 문구 · "사유: …", 비밀번호 칸 비움, 이동 0번 | ✓ 실패 |
| 아이디를 비우고 누른다 | 칸 옆 "아이디를 입력해주세요.", 로그인 처리 0번 | ✓ 검증 실패 |
| 이미 로그인했다 | 돌아갈 주소로 | — (이용자 · 업체 로그인과 같은 처리) |

## 3. 로그인 처리 — `POST /api/admin/login`

**동작 흐름**

1. 같은 사이트의 JSON 요청만 받는다(다른 사이트 form 이 로그인 쿠키를 심는 것 막기).
2. Next 서버가 백엔드 관리자 로그인(동기)을 부른다 — 재발급도 Next 서버가 부르므로 로그인 IP 와 재발급 IP 가 같다.
3. 되면 관리자 토큰 쿠키 2개와 계정 쿠키(아이디 · 권한 — 토큰과 같이 지운다)를 쓰고 비밀번호 변경 필요 여부를 돌려준다.
4. 안 되면 백엔드 실패 문구 · 칸 오류 · 정지 사유를 그대로 돌려주고 쿠키는 쓰지 않는다. 네트워크 · 백엔드 5xx 는 "잠시 뒤 다시"로 돌려준다.

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `login_id` · `login_pw` | ✓ | 화면이 검사한 값 그대로(서버도 같은 DTO 로 다시 검사) |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 백엔드 로그인이 된다 | 백엔드 로그인 1번 → 토큰 · 계정 쿠키 → 비밀번호 변경 필요 여부 | ✓ 정상 |
| 백엔드가 404 · 403 으로 거절한다 | 받은 문구 · 정지 사유 그대로, 쿠키 0개 | ✓ 실패 |
| 다른 사이트 요청 · JSON 아님 | 실패, 백엔드 0번 | — (공통 같은 사이트 검사 — 매니저 로그인 처리와 같다) |
| 네트워크 · 백엔드 5xx | 실패 + 다시 시도 안내 | — (매니저 로그인 처리와 같은 처리) |

## 4. 비밀번호 변경 — `PAGE /admin/password`

**동작 흐름**

1. 콘솔 틀 안의 화면 — "비밀번호 변경" 제목, "지금 로그인한 관리자 계정(아이디)의 비밀번호를 바꿉니다.", 상단 바의 "비밀번호 변경"을 강조한다.
2. 처음 로그인해서 왔으면 안내 띠 "처음 로그인했습니다. 새 비밀번호로 바꾼 뒤 콘솔을 쓰세요." 상단 바에서 들어오면 띠 없이 같은 화면.
3. 현재 · 새 비밀번호(8 ~ 20자, 영문과 숫자 필수, 특수문자는 !@#$%^&* 만)를 검사해 틀린 칸 옆에 오류를 보이고, 맞으면 비밀번호 변경(큐)을 부른다.
4. 되면(결과 없이 늦어져도 같다) "비밀번호를 변경했습니다." 안내 뒤 첫 화면으로 간다.
5. 안 되면(현재 비밀번호가 틀림 · 기존과 같은 새 비밀번호) 받은 문구를 보여 준다.

**입력**

| 필드 | 필수 | 설명 |
|---|---|---|
| `current_password` | ✓ | 현재 비밀번호(20자까지) |
| `new_password` | ✓ | 새 비밀번호(8 ~ 20자, 영문 + 숫자, 특수문자 !@#$%^&* 만) |
| `required` | | 처음 로그인해서 왔는지(`?required=1`) — 안내 띠 |

**결과**

| 상황 | 응답 | 테스트 |
|---|---|---|
| 맞는 현재 비밀번호와 규칙에 맞는 새 비밀번호로 바꾼다 | 변경(큐) 1번 → "비밀번호를 변경했습니다." → 첫 화면 | ✓ 정상 |
| 새 비밀번호에 숫자가 없다 | 칸 옆 DTO 문구, 변경 0번 | ✓ 검증 실패 |
| 현재 비밀번호가 틀렸다 · 기존과 같다 | 받은 문구(오류 팝업) | — (공통 실패 처리) |
| 로그인하지 않았다 | 관리자 로그인(돌아올 주소) | — (콘솔 틀 로그인 가드) |

## 데이터 변화

- 로그인 처리(3)가 관리자 토큰 쿠키(`admin_access_token` · `admin_refresh_token`)와 계정 쿠키(`admin_account` — 아이디 · 권한)를 쓴다. 로그아웃(1)은 셋을 지운다.
- 비밀번호 변경(4)은 백엔드 관리자 비밀번호를 바꾼다(큐). 바꾼 뒤 비밀번호 변경 필요 여부는 백엔드가 0 으로 둔다.
- 토큰 재발급(`admin/token-refresh`)은 이미 있다(`src/contracts/admin/api.ts` · `src/app/api/cookie/token-cookie.ts:41`).

## 결정한 것

- [x] 대시보드가 생기기 전(Phase 17)까지 첫 화면은 "대시보드는 준비 중이에요" 안내, 메뉴는 시안대로 5개를 모두 둔다(없는 화면은 눌러도 없는 화면) — 사용자 선택. 근거: 업체 콘솔 틀(Phase 10)도 화면보다 메뉴를 먼저 두었다.
- [x] 로그인 뒤 갈 주소 규칙(처음 로그인 → 비밀번호 변경, 아니면 돌아갈 주소)은 계산 테스트를 따로 두지 않는다 — 로그인 화면 ✓ 두 줄이 확인한다(사용자 선택, 업체 로그인과 같다).
- [x] 로그인은 Next 서버 route(`POST /api/admin/login/`)가 백엔드를 부른다 — 로그인 IP 와 재발급 IP 가 같게(AGENTS.md Auth "관리자 Phase 15 도 같은 모양으로").
- [x] 비밀번호 변경은 콘솔 틀 안 — 시안(`frontend/design/admin.html` A1-password)이 메뉴 · 상단 바와 함께 그리고 상단 바 "비밀번호 변경"을 강조한다(업체 비밀번호 변경은 메뉴 없는 카드 — 시안이 다르다).
- [x] 권한 배지 글자는 시안대로 총괄관리자(`SUPER_ADMIN`) · 관리자(`ADMIN`). 메뉴는 둘이 같다(시안 `admin.html:260`).
- [x] 로그인 실패 띠는 아이디 칸 위, 정지 사유는 "사유: …", 실패하면 비밀번호 칸만 비운다 — 시안 A1 로그인의 상태 그림.
- [x] 비밀번호 변경의 성공 안내 · 실패 문구는 업체 비밀번호 변경과 같이 오류 팝업 하나로 보인다(시안은 띠 — 공통 오류 팝업 규칙, 사용자 2026-11-15).

## 제안 (코드베이스 기반)

- 업체 · 관리자 로그인 처리 route 는 아이디 · 비밀번호 받기 · 실패 본문 넘기기 · 다시 시도가 같다(`src/app/api/manager/login/route.ts`) — 같은 부분을 route 공통 함수로 모으고 두 route 가 함께 쓴다(plan 에서).
- 콘솔 틀 상단 바 "비밀번호 변경" 링크는 지금 주소가 그 주소면 강조한다(`src/shared/components/console/ConsoleShell.tsx`) — 업체 비밀번호 변경은 콘솔 밖이라 영향이 없다.
