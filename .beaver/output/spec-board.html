Phase 2구현

모든 화면이 백엔드를 부르는 기반 — 동기 조회는 request, 상태를 바꾸는 쓰기는 큐(SSE) callQueue, 실패는 handleApiError 하나로 칸 옆 · alert 에 보여 준다. fetch 하나로 통일하고 예전 axios 래퍼를 지운다. 지침서 공통 DTO · 상수를 contracts/common 에 그대로 옮기고, 페이지 타입 · 페이지 버튼을 snake_case 와 시안 모양으로 바꾼다. 한국 시각 · 금액 · 요일 표시 유틸과 상태 이름 룩업을 둔다. 영역별 토큰 · 401 재발급은 Phase 3.

  • CASES:takeSseEventsdata: 두 줄 → data 를 \n 으로 이어 한 값

  • CASES:takeSseEventsdata 없는 "event: pending\n\n" → [{event: "pending", data: ""}]
  • CASES:callQueueaccepted → done {"store_id":1} → {store_id: 1} · fetch 1회 · method · Accept: text/event-stream · Content-Type: application/json · Authorization: Bearer t · 본문 JSON
  • CASES:callQueuedone null → null
  • CASES:callQueuefailed {status_code: 400, message, validation_errors} → ApiError(status 400, body 그대로) throw
  • CASES:callQueuepending {request_id, message} → null
  • CASES:callQueue한 이벤트가 두 조각으로 나뉘어 와도 → done data
  • CASES:callQueue스트림 전 401 JSON → ApiError(401) throw, 스트림을 읽지 않음
  • CASES:callQueuedone · failed · pending 없이 스트림이 끝남 → null
  • CASES:callQueuetoken null → Authorization 헤더 없음
  • CASES:requestGET query: {page: 1, keyword: undefined} → <API>/api/v1<path>?page=1, 본문 없음, JSON 반환
  • CASES:requestPOST body: {login_id: "a"} → Content-Type: application/json, 본문 {"login_id":"a"}
  • CASES:requesttoken "t" → Authorization: Bearer t
  • CASES:request400 실패 본문 → ApiError(400, 본문) throw
  • CASES:request204 · 빈 본문 → null
  • CASES:request502 HTML 본문 → ApiError(502, {message: "서버 응답을 읽을 수 없습니다.", validation_errors: null})
  • CASES:createQueryString{page: 1, keyword: "강남 역"} → "?page=1&keyword=%EA%B0%95%EB%82%A8%20%EC%97%AD"
  • CASES:createQueryString{page: 1, a: null, b: undefined, c: ""} → "?page=1"
  • CASES:createQueryString{a: null} · {} → ""
  • CASES:Pagination4 버튼 → movePage("4") 1회
  • CASES:Pagination2쪽에서 이전 · 다음 → movePage("1") · movePage("3")
  • CASES:Pagination현재 페이지 버튼 → movePage 미호출
  • CASES:Pagination1쪽 → 이전 버튼 막힘, 눌러도 미호출
  • CASES:Pagination마지막 쪽 → 다음 버튼 막힘, 눌러도 미호출
  • FAIL:validationApiError(400) + validation_errors 칸 있음 → 그 칸에 메시지, alert 미호출, 이전 칸 오류는 지움
  • FAIL:validationvalidation_errors 는 있는데 맞는 칸 없음 → alert(message) 1회
  • FAIL:validationvalidation_errors: null → alert(message) 1회
  • FAIL:networkApiError 가 아닌 오류(fetch TypeError) → 고정 문구 alert 1회
  • FAIL:abortAbortError → alert 미호출

규칙 6
  • 주소는 ${NEXT_PUBLIC_API_URL}/api/v1${path}${query} — 게이트웨이 하나만(로컬 http://localhost:3000).
  • 요청 · 응답 키는 snake_case 그대로. GET 은 query, 그 밖은 JSON 본문(Content-Type: application/json).
  • query 는 createQueryString — null · undefined · 빈 문자열은 빼고 키 · 값을 encodeURIComponent.
  • 큐는 Accept: text/event-stream 으로 fetch 스트림을 읽는다 — accepted 뒤 done · failed · pending 중 하나에서 끝난다. 이벤트 경계는 빈 줄(\n\n, CRLF 도 허용), 여러 줄 data: 는 \n 으로 잇고, : 로 시작하는 줄은 무시한다.
  • 큐 결과는 지침서 예시 그대로 done → data, pending → null (사용자 결정). 응답 DTO 가 null 인 API 는 done 과 pending 이 같은 null — 화면은 null 이면 그 리소스를 다시 조회한다(둘 다 맞는 처리).
  • 실패 본문은 동기 · 큐 같은 모양 {message, validation_errors, …} — 기능별 추가 필드(block_comment · payment_error_code)도 ApiError.body 에 그대로 남는다. JSON 이 아닌 실패 본문은 {message: "서버 응답을 읽을 수 없습니다.", validation_errors: null}.

ui기능 1 · TDD 4

시안의 색 · 글꼴 · 크기를 전역 토큰으로, 공통 UI 부품과 경로 모달 규칙을 코드로

PAGE /dev/ui · /dev/ui/modal-demo (개발 전용) · src/shared/components/ui/*
PAGE (개발 전용) · 공통 컴포넌트

Phase 1배포

25개 화면이 같이 쓰는 디자인 기반 — 시안의 색 · 글꼴 · 크기 토큰과 공통 UI 부품, 경로 모달 규칙을 만든다. 색은 전역 한 벌, 크기만 영역별(data-area="console")이라 같은 부품을 이용자 · 콘솔이 같이 쓴다. 개발 전용 /dev/ui 에서 모든 부품을 두 크기로 나란히 확인한다(운영 404).

TDD · 4건 · 생략 있음
  • FAIL:validationReasonModal(필수) — 사유가 비어 있거나 공백뿐이면 확인 버튼이 비활성이고, 눌러도 onConfirm 이 불리지 않는다
  • SUCCESSReasonModal — " 고객 요청 " 입력 후 확인 → onConfirm("고객 요청") 1회
  • FAIL:validationReasonModal(maxLength=5) — "123456789" 입력 → 칸에는 "12345", 확인 → onConfirm("12345") 1회
  • SUCCESSReasonModal(필수 아님) — 비운 채 확인 → onConfirm("") 1회

생략(위임형): 토큰 · Button · Input · Textarea · Field · Badge · Band · Switch · Chip · Segmented · Tabs · Card · Table · Modal · ConfirmModal · RouteModal · EmptyState · CopyButton · /dev/ui — 그리기와 이벤트 전달만, 실제 모습은 /dev/ui 로 본다

규칙 6
  • 색 토큰은 전역 한 벌, 이름은 콘솔 시안 기준(--ok · --danger · --neutral-bg …). 이용자 전용 색(--map-* · --kakao · --naver)만 더한다. 값은 세 시안과 같다(밝은 화면 한 벌).
  • 크기 토큰(기본 글자 · 컨트롤 높이 · 버튼 굵기 · 입력 여백 · 배지 높이)은 기본이 이용자(15px · 48px), [data-area="console"] 이 콘솔(14px · 40px). 영역 layout 이 data-area 를 붙인다.
  • 글꼴은 Noto Sans KR(400 · 500 · 700)을 next/font/google 로 — --font 가 그 변수를 쓴다.
  • 부품 스타일은 같은 폴더 <Name>.module.css, 색 · 크기는 토큰 var(--…) 만 쓴다(값을 직접 쓰지 않는다).
  • 모달은 브라우저 <dialog>(showModal()) — Esc · 바깥 막기 · 포커스는 브라우저 기본. 닫힘은 onClose 하나로 모은다.
  • 사유 입력 모달: 필수면 비어 있거나 공백뿐일 때 확인을 막고, 확인하면 앞뒤 공백을 뺀 사유를 넘긴다. maxLength 를 넘는 입력은 잘라서 받고 글자 수를 보여 준다.
